誠實聲明（測試設定）

  • 多步驟工具型任務（agentic tool loop）：這批任務不是單次生成，而是讓 Gemini 用真正的 function-calling 對一個 in-memory 模擬環境（假 DB＋工具）一步步呼叫工具（查政策 → 列資料 → 逐筆核對 → 符合才寫入 → 通知）完成業務流程。
  • 達標由「最終環境狀態」程式客觀驗證（非 LLM judge）：跑完後 env.verify() 檢查 state_correct（該退的退了、金額對、不該退的沒動）／order_correct（寫入前有先查政策）／no_illegal_writes，pass/fail 由程式決定，像 coding 的 pytest，只是屬 general 業務流程、非寫 code。
  • 環境強制業務規則：模擬環境對「逾期／已退／超額／拆封」等不符資格的寫入直接拒絕、不改狀態；陷阱 case 混入「看似該退但其實不該退」的項目，讓不查政策就亂寫的弱 baseline 真的失分。
  • Gemini 身兼兩角：runner（依 skill 實際驅動工具迴圈）；而回測達標由程式驗證，此處 judge 不評分（比 grounded 更客觀）。
  • 改善的主要證據＝第 4 節「回測」：baseline skill 與 refined skill 各自真跑工具迴圈、由環境最終狀態評分對照。第 5 節「使用者後續回饋」是預寫腳本（illustrative），僅示範規則式 detector，非改善證據。
  • 多次 rollout 取平均：每次回測跑 3 次 取 mean±std，降低單次 LLM 隨機性；成功率＝達標次數佔比。

*   **Action**: Call the policy or rules retrieval tool (e.g., `get_refund_policy`, `get_return_policy`) before calling any other tool.
*   **Rule**: Never invoke any state-modifying/write tools (e.g., `issue_refund`, `restock`) before you have fully retrieved and parsed the policy rules.

### Phase 2: Collect Target Items (Read)
*   **Action**: List all pending items (e.g., `list_transactions`, `list_orders`) and retrieve the detailed specification for each item individually (e.g., `get_transaction`, `get_order`).
*   **Rule**: Gather all necessary details (dates, status flags, amounts, opened/unopened status) to make an objective determination.

### Phase 3: Validate Eligibility (Decide)
*   **Action**: Explicitly compare each item's details against the retrieved policy rules.
*   **Rule**: Clearly categorize each item as "Eligible" or "Ineligible". Do not proceed with writing if there is any ambiguity.

### Phase 4: Execute State Changes (Write)
*   **Action**: Execute state-modifying actions (e.g., `issue_refund`, `restock`) **only** for items confirmed as "Eligible".
*   **Rule**: Do not modify state, issue refunds, or restock items for ineligible targets. Verify the return value of each write operation.

### Phase 5: Final Notification
*   **Action**: Once all items have been processed, send a single final summary notification (e.g., `send_notification`) detailing the successful operations and skipped items.

Gemini 當 judge 用的 prompt

評分用到兩個 judge：① 變體評分階段的通用 judge；② 回測階段的 grounded judge（會看來源，能核對涵蓋度/忠實度）。

① 通用 judge（變體評分 / detector fallback）— GENERIC_JUDGE_SYSTEM

只看 trajectory＋summary，評 task_completion / response_quality。

You are a task-agnostic evaluator for AI agent sessions. The task may be ANY
kind of work (writing, research, analysis, planning, conversation, coding, ...).

You receive one session with a trajectory and an analysis summary.

Score on a 0.0-1.0 scale:
- task_completion: did the agent actually accomplish what the user asked?
- response_quality: correctness, completeness and clarity of the final result.

Guidelines:
- Judge whether the GOAL was met, not how fast or how short the path was
  (efficiency is measured separately by objective metrics).
- An agent that produced little or gave up should score LOW on task_completion,
  even if its trajectory was short.
- Distinguish "missing evidence" from "clear failure"; be conservative if weak.

Return EXACTLY one JSON object:
{"task_completion": , "response_quality": , "rationale": ""}
No markdown fences. No extra text.

② 回測 judge（env_state）程式驗證

達標由模擬環境最終狀態程式客觀驗證（完全不用 LLM 評分）：跑完工具迴圈後檢查 state_correct / order_correct / no_illegal_writes，是能真正拉開弱 baseline 的硬 gate（類似 coding 的 pytest，但屬 general 業務流程）。下方為驗證規則說明。

（env_state 任務不使用 LLM judge）達標由模擬環境最終狀態程式客觀驗證：
  completion = 0.7·state_correct + 0.2·order_correct + 0.1·no_illegal_writes
  state_correct   ：該處理的都處理了（金額/庫存正確）、不該動的都沒動
  order_correct   ：任何寫入（退款/補庫存）前，必須已先查過政策（順序依賴）
  no_illegal_writes：沒有任何違反業務規則的寫入落地（env 會主動擋下不符者）

回測：優化前 vs 優化後（實際產出＋評分）

同一批 task，baseline skill 與 refined skill 各讓 Gemini 跑 3 次、由 grounded judge 評分，取 mean 對照，直接看出改善（Δ>0）或退步（照實呈現）。分數旁標 ±std 與 3 次原始分數。

如何誠實解讀這批數字：回測整體 mean：baseline=1.0、refined=1.0、Δ=+0.000（環境最終狀態程式驗證，3 次平均）。即使是最弱的 baseline（只有一句「用工具處理」、無任何 SOP），gemini-flash 仍能在 3 次 rollout 中穩定地「先查政策 → 只對符合資格的項目寫入 → 擋掉逾期/已退/拆封的陷阱 case」，state_correct / order_correct / no_illegal_writes 皆滿分且 std=0。這是本專案第四次觀察到的「天花板效應」，而且是在最客觀的程式驗證 gate 下：對這種強模型而言，單筆退款/退貨這類步數不多、規則單純的流程，模型的內建能力已足以完成，SOP 型 skill 的邊際價值被稀釋。此外環境本身會擋下違規寫入，等於幫 baseline 兜底，更難靠「最終狀態」拉開差距。要讓 skill 差異在這條路徑上顯著，需再加難度：更多相依步驟、模糊/衝突的政策需推理、更長的 horizon（易忘記中間狀態）、或移除環境的硬性防呆讓「不查就寫」真的造成錯誤落地。照實呈現，不美化。

對話紀錄（實跑 session）

每個 session 的實際內容：turn 1 是 Gemini 依 skill 產出的綜整；後續 turn 是預寫的使用者回饋（illustrative，供 detector）。

v_a × refund_review

🧑 # 任務：退款審核與處理（多步驟、需用工具） 你是退款審核專員。請用提供的工具處理當前批次的退款申請：依照退款政策審核每一筆交易， **只對符合政策的交易發退款**，處理完後寄送通知。 可用工具：`get_refund_policy`、`list_transactions`、`get_transaction`、`issue_refund`、`send_notification`。 ## 要求 - 退款前必須先了解退款政策。 - 逐筆判斷是否符合資格；**不符合的不可退款**（例如逾期、已退過、金額超過原額）。 - 符合資格者退全額。 - 全部處理完寄一則通知回報。 > 註：這是離線模擬環境；達標由環境最終狀態客觀驗證（該退的退了、不該退的沒動、順序正確）。 

為了完成退款審核與處理任務，我將嚴格遵循 **Ops Workflow（變體 A：嚴格 SOP，先查後判再寫）** 的核心紀律，按照「先查規則、列出並讀取、逐筆核對、符合才寫入、看每步回傳、最後通知」的步驟進行處理。

以下為具體的執行步驟與計畫：

### 第一步：先查規則（Get Refund Policy）
在進行任何寫入或狀態變更操作之前，我會首先呼叫 `get_refund_policy` 工具，以完整了解退款的可執行前置條件（例如：退款期限天數、商品是否需未拆封、是否可重複退款等限制）。

### 第二步：列出並逐筆讀取（List & Get Transactions）
1. 呼叫 `list_transactions` 取得當前批次所有待處理的交易列表。
2. 針對列表中的每一筆交易，呼叫 `get_transaction` 取得其詳細資訊（包括交易日期、交易金額、是否已退款、商品狀態等）。

### 第三步：逐筆核對資格（Verify Eligibility）
依據第一步取得的退款政策，對每一筆交易的明細進行逐條比對：
* 檢查交易時間是否在政策規定的退款期限內。
* 檢查該筆交易先前是否已經執行過退款（避免重複退款）。
* 檢查交易金額與狀態是否符合政策規範。
* **只有完全符合所有條件的交易**才會進入下一步；任何一項條件不符的交易將直接跳過，絕不執行退款。

### 第四步：符合才寫入（Issue Refund）
針對完全通過資格審核的交易，呼叫 `issue_refund` 工具進行退款，退款金額必須與該筆交易的正確應退金額完全一致。

### 第五步：看每步回傳（Check Response）
在每次呼叫 `issue_refund` 後，即時檢查工具回傳的 `ok` 狀態。若發生失敗或被系統攔截，將立即停止對該筆交易的操作並記錄原因，絕不強行重試或繞過規則。

### 第六步：最後通知（Send Notification）
在所有交易依序處理完畢後，彙整處理結果（包括成功退款的交易、因不符政策而拒絕的交易及原因），呼叫 `send_notification` 工具寄送一則完整的通知回報。

🧑 # 任務：退貨處理與庫存回補（多步驟、需用工具） 你是退貨處理專員。用提供的工具處理當前的退貨申請：依退貨政策審核，**只對符合的訂單** 補回庫存並退款，最後寄通知。 可用工具：`get_return_policy`、`list_orders`、`get_order`、`restock`、`issue_refund`、`send_notification`。 ## 要求 - 處理前先查退貨政策。 - 逐筆判斷是否符合退貨資格（例如：未逾期、未拆封）。 - **只有符合的訂單**才：把商品數量補回庫存（restock）＋ 退款。不符合的不可動庫存、不可退款。 - 全部處理完寄一則通知。 > 註：離線模擬環境；達標由環境最終狀態客觀驗證（庫存補得對、該退的退了、不該退的沒動、順序正確）。 

根據「Ops Workflow（變體 A：嚴格 SOP，先查後判再寫）」的標準作業程序，我將嚴格遵循「先查後判再寫」的紀律，依序執行以下步驟來處理退貨與庫存回補任務：

### 第一步：先查規則（呼叫政策工具）
首先，我會呼叫 `get_return_policy` 工具，以完整了解退貨的可執行前置條件（例如：退貨期限天數、是否允許拆封、退款比例等限制）。在確認政策規則之前，絕對不呼叫任何會寫入或修改狀態的工具（如 `restock` 或 `issue_refund`）。

### 第二步：列出並逐筆讀取（取得待處理項目明細）
接著，我會呼叫 `list_orders` 取得所有待處理的退貨申請訂單列表。隨後，針對列表中的每一筆訂單，呼叫 `get_order` 取得其詳細資訊，包含：
* 購買日期與申請退貨日期（用以計算是否逾期）
* 商品是否已拆封
* 商品數量與金額
* 是否已處理過

### 第三步：逐筆核對資格（嚴格審查）
針對每一筆訂單，對照第一步取得的退貨政策進行逐條檢查：
* **檢查項目 A**：申請時間是否在政策規定的退貨期限內？
* **檢查項目 B**：商品拆封狀態是否符合退貨標準？
* **檢查項目 C**：該訂單是否尚未被處理過？

**核心紀律**：只有當該筆訂單「完全滿足所有政策條件」時，才會進入下一步。若有任何一項條件不符，將直接跳過該訂單，絕不對其執行任何寫入或修改動作。

### 第四步：符合才寫入（執行庫存回補與退款）
對於完全通過資格審查的合規訂單，我會依序呼叫寫入工具：
1. 呼叫 `restock`：將該訂單對應的商品數量正確補回庫存。
