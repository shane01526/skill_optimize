誠實聲明（本輪設定）

  • 為什麼有這一輪：前一輪 agentic 任務第 4 次撞天花板——連弱 baseline 都拿滿分。主因是任務步數少、且環境有硬性防呆（違規寫入被擋，等於幫 baseline 兜底）。本輪針對性拉滿難度。
  • 四軸難度：① 多相依步驟（查政策→判資格→排序→受預算核銷→連動扣點→通知）；② 政策衝突需推理（fraud > FINAL 不可退 > VIP 窗 > 基本窗）；③ 長 horizon（每日預算上限，須累計已退金額、超過就 defer）；④ 移除硬性防呆。
  • 關鍵：環境不再把關：issue_refund / deduct_loyalty 照單全收、永遠回 ok，不檢查資格/預算/重複。於是「不查就寫」「退不該退的」「超預算」「漏扣點」的錯誤會真的落地，只能靠 verify() 事後比對正確最終狀態抓出來——這次 no_illegal_writes 會真的變動。
  • 達標＝程式客觀驗證（非 LLM）：completion = 0.7·state_correct + 0.2·order_correct + 0.1·no_illegal_writes。驗證器見 refiner/sim_env.py::make_approval_env。
  • 本報告在比什麼：同一個深難任務，用通用 SOP skill（ops-workflow）與領域專用 skill（ops-approval，寫死了優先序/預算/扣點）各跑一次完整精煉＋回測，看哪一套能把 baseline 拉開。
  • 改善主證據＝第 2 節回測（baseline vs refined 真跑工具迴圈、程式驗證）。變體評分階段仍受 conversation.json 腳本回饋影響（illustrative，非改善證據）。每組跑 3 次取 mean±std。

# Ops Workflow (Strict SOP: Check-Before-Write)

This workflow enforces a strict sequence of operations to prevent premature writes, policy violations, or budget overruns. You must execute these steps sequentially and never hallucinate tool outputs.

### Step 1: Upfront Policy & Rule Retrieval
- **Action**: Call the policy or configuration retrieval tools first (e.g., `get_refund_policy`).
- **Rule**: Never assume or hallucinate limits, budgets, priority rules, or eligibility windows. Read them directly from the system source of truth before proceeding.

### Step 2: Batch Fetching & Offline Evaluation
- **Action**: Retrieve all pending requests or items (e.g., `list_requests`, `get_request`).
- **Rule**: Evaluate eligibility for *all* items offline before executing any write operations. Filter out ineligible items based on strict exclusion criteria (e.g., fraud flags, non-refundable promo codes, expired windows).

### Step 3: Priority Sorting & Constraint Simulation
- **Action**: Sort the eligible items according to the priority rules (e.g., VIP status first, then ID ascending).
- **Rule**: Perform a dry-run calculation of cumulative constraints (such as daily budget caps or point balances). Track the running balance step-by-step. Stop processing further requests the moment a cumulative limit is reached or exceeded.

### Step 4: Sequential Execution & Verification
- **Action**: Execute write operations (e.g., `issue_refund`, `deduct_loyalty`) only for the validated, prioritized, and budget-compliant items.
- **Rule**: If any write operation fails or returns an unexpected error, halt the workflow immediately to prevent inconsistent states.

# Refund Approval SOP

Follow this strict step-by-step procedure to process refund requests. Do NOT hallucinate or summarize results without executing the corresponding tools.

## Step 1: Retrieve Policy and Constraints
- Call `get_refund_policy` first to fetch current rules (daily budget limits, tier deadlines, and loyalty point deduction formulas).

## Step 2: List and Inspect Requests
- Call `list_requests` to get all pending requests.
- Call `get_request` for specific details if needed.

## Step 3: Evaluate Eligibility & Priority
Evaluate each request strictly in order of priority:
1. **Fraud Check**: If `fraud = true`, reject immediately.
2. **Promo Code**: If promo code is `FINAL`, reject immediately (even for VIPs).
3. **Time Window**: Verify request date against purchase date based on customer tier (e.g., VIP vs. regular deadlines).

## Step 4: Enforce Budget and Process Transactions
- Sort eligible requests prioritizing VIPs first.
- Keep a running total of approved refunds. Do NOT exceed the daily budget limit.
- For each approved refund:
  1. Call `issue_refund` with the exact amount.
  2. Calculate loyalty point deduction: `floor(refund_amount / 10)` (or as specified by policy) and call `deduct_loyalty`.
  3. Call `send_notification` to notify the customer.

## Step 5: Report Summary
Provide a final breakdown of approved, rejected, and skipped (due to budget) requests with their respective transaction IDs.

誠實結論

通用家族：baseline mean=0.467、精煉後 Δmean=-0.267； 專用家族：baseline mean=0.348、精煉後 Δmean=+0.652。 本輪終於打破天花板：專用 ops-approval、通用 ops-workflow 家族的弱 baseline 在四軸難度＋無防呆下真的失分（baseline mean 明顯低於 1.0），skill 差異首次在最客觀的程式驗證 gate 下顯現。移除環境防呆讓「不查政策就亂退／退 fraud/FINAL/逾期／超預算／漏扣點」的錯誤真的落地，是關鍵。 其中領域專用 skill 的 baseline 更低——專用任務對通用 SOP 更不友善，也印證『把領域規則寫進 skill』確有價值。 最關鍵的對比：把同一批證據餵給精煉，領域專用 skill 精煉後大幅拉高（Δ=+0.652，refined 達 1.0），而通用 SOP skill 精煉後沒有幫助、甚至退步（Δ=-0.267）。這正是 skill 精煉的核心價值：對規則明確的領域任務，光有『先讀後寫、逐條核對』的通用紀律不夠，必須把領域規則（政策優先序、每日預算累計、連動扣點）寫進 skill——通用 SOP 缺了這些領域知識，模型仍會踩爆 fraud/FINAL/超預算/漏扣點的陷阱。
