Skill 精煉機制 — 詳細說明

從多個 skill 變體的使用紀錄中，篩選出更有效率、效用的版本，精煉成標準化共用 Skill。
個人版 MVP · 實驗驅動（Phase 1）＋ Log 探勘（Phase 2）· 基礎參考：SkillClaw（AMAP-ML）
本頁對照表數字為真實 Gemini（gemini-flash-latest）api 模式實跑；版本 B 對照為離線 mock。

1

總覽

一句話：同一目標寫多個 skill 變體 → 讓它們跑同一批任務 → 用客觀+行為訊號評分 → 從勝出變體萃取做法 → 精煉成新版並產出對照表。

需求：從大量員工使用 Codex Skill 的紀錄中，透過 Log 分析找出可共用的有效做法，整理、合併、精煉成標準化 Skill。 目前無集團 Log／同事 Skill，故先做個人版 MVP，以 coding 為首個實驗場景（好判斷好壞），流程可擴展到任何場景。

2

Pipeline 流程

兩個階段共用同一套後段（摘要→分組→精煉→驗證→registry）；差別只在「資料來源」與「評分方式」。

本機現況：這台是 Codex Desktop app（狀態存 SQLite），目前無 rollout log； Phase 2 需先安裝經典 CLI 累積對話。故本頁實跑走 Phase 1 的 api 模式（真 Gemini 執行任務 + 評分）。
3

skill_id / 版本 / Registry

Codex log 沒有欄位記錄「用了哪個 skill」；解法是上架就綁 skill_id，並從 log 反查實際讀取的 SKILL.md。

---
skill_id: coding-debug
name: coding-debug
version: 1.0.0
description: ...
---
  • skill_id：作者提供的 slug（如 coding-debug）；未提供時系統以 SHA-256(name)[:12] 產生。
  • version 每次內容變更 +1；content_sha 供衝突偵測。
  • history（上限 20）記錄 {version, content_sha, timestamp, action, rationale}。
  • runner 明確記錄 actual_used_skill_ids，不靠事後推斷。

4

評分機制

每個 (變體×task) session 先算通用效率指標，再依任務類型分流評分，最後跨 task 平均選出 winner。降低對 LLM 的依賴是核心設計。

4.1 評分分流（決策樹）

4.2 通用效率指標（不依賴 LLM、任何場景都能算）

對應 refiner/generic_metrics.py，全部從 session 既有欄位取得。「越少越好」→ 在 cohort 內反向正規化。

指標來源方向權重
num_turns對話輪數越少越好0.35
elapsed_sec執行時間（ended−started）越少越好0.25
num_tool_calls工具呼叫總數越少越好0.15
tool_error_rate工具錯誤佔比越低越好0.15
response_chars回覆總字數（≈ token 成本）越少越好0.10
  • cohort 分組：明確按 (goal, task) 分桶，只在「同 goal 同 task 的變體群」內做 min-max 反向正規化 （不跨 task／goal 比較，避免難易度污染）。最小值→1.0、最大值→0.0；全相等或單一變體→1.0（中性）。
  • 缺值：某項在 cohort 全缺（如 mock 無真實時間）→ 不計入，權重按剩餘項重分配（分母只算有值的項）。
  • 防呆：效率「越少越好」，單獨用會獎勵擺爛 → 一定與「完成度」相乘（先確認完成，再比效率）。

評分標準（單一指標怎麼從原始值變成 0..1）

正規化（越少越好）：norm = (cohort最大值 − 本值) / (cohort最大值 − cohort最小值)
tool_error_rate（本身已 0..1）：norm = 1 − error_rate
efficiency = Σ(norm_i × 權重_i) / Σ(有值項的權重)

實算範例（同一 cohort 三個變體的 num_turns）

假設某 (goal, task) 下三個變體的對話輪數分別為 3 / 6 / 9（cohort min=3, max=9）：

變體num_turns計算該項 norm
v_a3（最少）(9−3)/(9−3)1.0
v_b6(9−6)/(9−3)0.5
v_c9（最多）(9−9)/(9−3)0.0

每個指標都這樣算出 0..1，再依上表權重加權平均，得該 session 的 efficiency_score。 若 cohort 三個變體輪數都一樣（如都 5）→ max=min → 該項一律給 1.0（無鑑別度、不懲罰）。

4.3 達標判定：規則式 detector（使用者行為訊號，零 LLM）＋ LLM 後備

對應 refiner/completion_detector.py。思路來自 IR／推薦系統的 implicit feedback——不問「滿意嗎」， 看使用者接下來的回覆。純關鍵詞／正則／difflib，不呼叫 LLM。

訊號方向權重觸發例
positive（確認滿意）達標 ↑1.0「就是這個」「thanks」「lgtm」
adopt / adopt_tool（採用產物）達標 ↑1.0 / 0.7「已套用」；成功 apply_patch/write
continue_next（接續新任務）達標 ↑（弱）0.6「接著寫英文版」「next」
session_end（結束無追問）達標 ↑（弱）0.25回覆後無 follow-up、無錯誤
negative（否定、要求重來）未達標 ↓1.0「不對」「重寫」「wrong」
coding_retry（要求繼續修）未達標 ↓0.9「還是失敗」「still failing」
reformulation（重述同一需求）未達標 ↓0.8×相似度下一輪 prompt 與前輪相似度 ≥ 0.7

評分標準（訊號 → completion / confidence）

pos = Σ正向訊號權重     neg = Σ負向訊號權重
raw = (pos − neg) / (pos + neg)        # ∈ [−1, 1]
completion = (raw + 1) / 2             # ∈ [0, 1]，≥0.5 判定「達標」
confidence = tanh(pos + neg)           # 訊號越多越有信心；門檻 0.5

實算範例

使用者後續回覆命中訊號pos / negcompletionconfidence判定
「讚，就是這個，謝謝」positive(1.0)1.0 / 01.0tanh(1.0)=0.76 ≥0.5 → 用規則達標
「不對，這不是我要的，重寫」+「還是不行」negative×2(2.0)0 / 2.00.0tanh(2.0)=0.96 → 用規則未達標
「接著幫我寫英文版」→「OK」continue_next(0.6)+positive(1.0)1.6 / 01.0tanh(1.6)=0.92 → 用規則達標
單輪、無使用者後續回覆（無訊號）0 / 00.50.0 < 0.5 → 退回 LLM交給 judge
限制：行為訊號在多輪真實對話最有效（Phase 2）。Phase 1 headless 單輪、無後續回覆 → confidence=0 → 自動退回 LLM judge（末列）。對照表 general 列標有 completion_source（rule／llm）。

4.4 coding 專用：pytest 硬指標 + 四維 LLM judge 軟指標

硬指標（客觀 ground truth）— run_pytest

在該 (變體×task) 的獨立 workspace 跑 pytest -q，用 regex 抓 N passed / N failed / N error：

情境passed/totalpass_rateall_pass（決定成功）
全部通過5 / 51.0✓
部分通過3 / 50.6✗
多數失敗2 / 50.4✗
找不到測試 / timeout / 例外0 / 00.0✗

total = passed + failed + errors；all_pass = (total>0 且 passed==total)， 是 coding 任務 _success 的判定依據。

軟指標（LLM judge）— JUDGE_SYSTEM，四維加權

維度評什麼權重1.0 / 0.5 / 0.0 例
task_completion是否達成 coding 目標（測試通過是強證據）0.55全過 / 部分過 / 全錯
response_quality修正的正確性、完整性、清晰度0.30乾淨最小修 / 可用但雜 / 誤導
tool_usage工具使用是否適當有效0.10精準 / 尚可 / 亂用
efficiency是否避免無謂重試／繞路0.05直達 / 小繞 / 鬼打牆
judge.overall = 0.55·task_completion + 0.30·response_quality
              + 0.10·tool_usage    + 0.05·efficiency   （各維 clamp 到 [0,1]）

本次 Gemini 實跑（task_001 · v_a）：四維皆 1.0 → overall = 0.55·1.0 + 0.30·1.0 + 0.10·1.0 + 0.05·1.0 = 1.0。 Gemini 一次就把 String Calculator 全部修對（5/5 通過），故各維滿分；rationale： 「single turn、100% pass rate、correct/complete/efficient」。 公式示意：若四維為 0.8/0.8/0.85/0.8 → overall=0.803。 真實 LLM 模式下四維由模型實際評分、會分化。解析失敗或任一維非數字 → 回 None（該 session 只用硬指標）。

4.5 合成綜合分（依任務類型）＋ 實算範例

# coding：原 pytest+judge 為主體，效率僅 ±5% 微調（向後相容）
base  = 0.6 × pass_rate + 0.4 × judge.overall
score = base × (0.95 + 0.05 × efficiency)

# general：完成度為主體，效率在已完成前提下加成 ≤40%
score = completion × (0.6 + 0.4 × efficiency)

4.6 兩個容易混淆的點

三種 judge 來源，公式相同：① 版本 A 真實 LLM（JUDGE_SYSTEM） ② 版本 A 離線 mock（base=0.8）③ 版本 B SkillClaw 原生 session_judge——同一組四維權重。
「評分閘」≠「發布閘」：綜合分用來比較變體選 winner； verifier.py 的 0.75 門檻是另一道獨立的「精煉版能否發布」閘 （grounded / preserves value / specificity / safe 四 check）。

精煉前 / 精煉後對照表

左側是各變體實測分數（綜合分以長條視覺化），右側是精煉前→後的 skill 內容與 diff。

發布閘：score = 0.98 / 門檻 0.75 → accept（grounded_in_evidence=1.0 preserves_existing_value=1.0 specificity_and_reusability=1.0 safe_to_publish=1.0 ）

精煉理由：Variant B achieved the highest scores on coding tasks (0.999 and 0.992) by treating tests as specifications and listing concrete edge cases (empty strings, delimiters, boundary filters). Variant A also performed very well (0.982) and offered a highly structured workflow (reproducing first with pytest, locating minimal modification points, and incremental verification). Merging these two approaches provides a highly effective, structured debugging guide that prevents over-engineering and ensures robust edge-case coverage.

# Coding Debug (代碼除錯與測試修復)

## 核心原則：以測試為規格，最小化修改

1. **重現並定位問題 (Reproduce & Locate)**
   - **先執行測試**：直接執行測試指令（如 `pytest -q`），閱讀第一個失敗的斷言 (Assertion) 與 Traceback，確認能穩定重現。
   - **定位最小修改點**：從 Traceback 往回追溯出錯的程式碼行，專注於該處，**切忌盲目重寫大片程式碼**。

2. **以測試為規格進行對照 (Treat Tests as Specifications)**
   - 將測試案例視為功能規格，逐一列出並檢查以下常見邊界與分支：
     - **空輸入/極端值**：空字串 `""`、`None`、`0`、空陣列等。
     - **單一值/常規值**：單個元素、標準輸入。
     - **邊界條件**：上界/下界過濾（例如大於 1000 需忽略、負數需拋出異常等）。
     - **多重格式/分隔符**：是否支援多種分隔符（如 `,` 與 `\n`）、自定義分隔符。
   - 逐條對照目前實作，找出「哪些規格/分支尚未被處理」。

3. **最小修改與分段驗證 (Minimal Change & Incremental Verification)**
   - **一次只補一個缺失分支**：針對缺少的 Case 補上對應的 `if/else` 分支或邏輯，修改完立即重跑相關測試。
   - **分段驗證**：先確保當前修改的測試通過，最後再執行完整測試套件，確保沒有引入回歸 Bug (Regression)。

6

與 SkillClaw 的關係：沿用什麼、差異在哪

本專案借用 SkillClaw 的「精煉引擎」後段骨架，但在前端（實驗設計）與評分（去 LLM）兩頭做了它沒有的延伸。本節先講設計差異，再附版本 A／B 實跑對照。

6.1 沿用的核心（後段精煉流程幾乎一致）

6.2 關鍵差異（本專案的延伸）

面向SkillClaw 原生本專案（版本 A）
session 來源 被動：client proxy 攔截 /v1/chat/completions，錄下使用者真實日常對話，背景非同步 evolve 主動實驗驅動：手寫多個 skill 變體 × golden task，由 runner 跑出受控 session
選優機制 無「多變體 PK」；拿同一 skill 的歷史 session 直接 evolve 變體對照：_variant_aggregate 跨 task 平均選出 winner，才送進 execution
評分 / 達標 幾乎全靠模型：PRM（per-turn majority vote）+ session_judge（LLM 四維）+ benchmark 多層去 LLM：pytest 硬指標 + 通用效率（輪數/時間/成本）+ 規則式行為 detector，LLM 只當後備
合併衝突 主動：多來源撞名 → _detect_conflict(SHA) + execute_merge(LLM 合併) 有能力（execution 含 merge prompt），但 MVP 單一 goal 尚未觸發
發布 / 分享 重架構：publish_mode(direct/review/validated) + Nacos/OSS 上架 + 客戶端投票 + 集團 sharing 精簡：本機 registry.json + 上架驗證（欄位/唯一性），去掉 proxy/OSS/dashboard/Nacos
執行環境 常駐 client proxy + evolve server + 共享儲存 單機、可離線、以檔案為主（logs/ → output/）
一句話：SkillClaw =「從既有真實 log 被動 evolve、靠 LLM 評判、面向集團分享」； 本專案版本 A =「主動造變體實驗、盡量用客觀/行為訊號評判、個人版可離線」。保留其精煉引擎骨架， 在前端（實驗設計）與評分（去 LLM）兩頭延伸。

已知陷阱與擴展路徑

文件點出的三個陷阱各有對策；評分層與資料源都設計成可從個人 MVP 擴展到集團規模。

三個陷阱 → 對策

  • log 沒記錄用哪個 skill → 上架綁 skill_id，log 反查 actual_used_skill_ids。
  • task_complete ≠ 成功 → pytest 通過率 + judge + 行為 detector 當成功訊號。
  • 重複 pattern ≠ 有效 → verifier 四分數閘（≥0.75）保守把關。

個人 → 集團 擴展

  • 資料源：個人實驗 log → 集團 Codex rollout（Phase 2 normalizer 已備）。
  • 評分：coding pytest → 各 BU golden dataset + 對應 judge／checker；通用效率與行為訊號跨場景通用。
