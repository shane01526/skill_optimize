Skill 精煉機制 — 詳細說明

從多個 skill 變體的使用紀錄中，篩選出更有效率、效用的版本，精煉成標準化共用 Skill。
個人版 MVP · 實驗驅動（Phase 1）＋ Log 探勘（Phase 2）· 基礎參考：SkillClaw（AMAP-ML）
本頁數字為 api 模式實跑：Gemini（gemini-flash-latest）同時擔任 runner（實際執行任務、修 code）與 judge（評分）；版本 B 對照為離線 mock。
評分機制已從 coding／general 擴展為可插拔的 judge 家族（grounded／ppt_outline／cross_doc／json_schema／env_state），並支援多步驟 agentic 工具型任務（真 function-calling ＋ 最終狀態程式驗證）。完整說明見「評分機制詳解」分頁。

總覽

一句話：同一目標寫多個 skill 變體 → 讓它們跑同一批任務 → 用客觀+行為訊號評分 → 從勝出變體萃取做法 → 精煉成新版；前後效果由各場景的 E2E 測試報告呈現。

需求：從大量員工使用 Codex Skill 的紀錄中，透過 Log 分析找出可共用的有效做法，整理、合併、精煉成標準化 Skill。 目前無集團 Log／同事 Skill，故先做個人版 MVP，以 coding 為首個實驗場景（好判斷好壞），流程可擴展到任何場景。

2

Pipeline 流程

兩個階段共用同一套後段（摘要→分組→精煉→驗證→registry）；差別只在「資料來源」與「評分方式」。

本機現況：這台是 Codex Desktop app（狀態存 SQLite），目前無 rollout log； Phase 2 需先安裝經典 CLI 累積對話。故本頁實跑走 Phase 1 的 api 模式（真 Gemini 執行任務 + 評分）。
同一套後段、多種場景：這條後段流程之上，建了一個 E2E 測試矩陣。 runner 支援兩種型態：單次生成（一般 general 任務）與 agentic 工具迴圈 （真 Gemini function-calling 對 in-memory 模擬環境一步步操作）。評分的 judge 可依 task 插拔 （task.json 的 judge 欄位決定），達標從「LLM 對照」到「程式硬驗證」都有。詳見「評分機制詳解」分頁的 judge 家族，與第 7 節場景矩陣。

skill_id / 版本 / Registry

Codex log 沒有欄位記錄「用了哪個 skill」；解法是上架就綁 skill_id，並從 log 反查實際讀取的 SKILL.md。

---
skill_id: coding-debug
name: coding-debug
version: 1.0.0
description: ...
---
  • skill_id：作者提供的 slug（如 coding-debug）；未提供時系統以 SHA-256(name)[:12] 產生。
  • version 每次內容變更 +1；content_sha 供衝突偵測。
  • history（上限 20）記錄 {version, content_sha, timestamp, action, rationale}。
  • runner 明確記錄 actual_used_skill_ids，不靠事後推斷。

6

已知陷阱與擴展路徑

文件點出的三個陷阱各有對策；評分層與資料源都設計成可從個人 MVP 擴展到集團規模。

三個陷阱 → 對策

  • log 沒記錄用哪個 skill → 上架綁 skill_id，log 反查 actual_used_skill_ids。
  • task_complete ≠ 成功 → pytest 通過率 + judge + 行為 detector 當成功訊號。
  • 重複 pattern ≠ 有效 → verifier 四分數閘（≥0.75）保守把關。

個人 → 集團 擴展

  • 資料源：個人實驗 log → 集團 Codex rollout（Phase 2 normalizer 已備）。
  • 評分：coding pytest → 各 BU golden dataset + 對應 judge／checker；通用效率與行為訊號跨場景通用。
  • 分享：本機 registry JSON → SkillClaw sharing / OSS / dashboard（版本 B）。
評分

評分機制詳解

這一頁把「一個 session 怎麼變成一個分數、多個變體怎麼選出 winner」講清楚。核心設計理念： 盡量用客觀證據評分、把 LLM 當最後手段。閱讀順序：先看設計原則與架構，再逐層看各評分元件，最後看 3 個實算範例。

0 導讀 1 設計原則·客觀性光譜 2 兩層架構總覽 3 通用效率指標 4 judge 家族（general/coding/agentic） 5 合成公式 6 實算範例（3 個） 7 容易混淆的點
本次實跑 Gemini 身兼兩角，請勿混淆：
  1. runner（執行任務）：api 模式下 Gemini 真的當 coding agent 去修 code，把修好的程式寫回 workspace。 → 這一步的產出由 pytest 客觀驗證（pass_rate 是測試跑出來的，不是 Gemini 自評）。
  2. judge（評分）：對執行結果打四維軟分數。
副作用：Gemini 能力足以無視 skill 差異、把這種簡單 coding 任務全部修對（三變體 pass_rate 都 1.0）， 因此 coding 難顯出 skill 高下——差異改由 general 任務與效率分拉開。若只想單純測「LLM as a judge」， 應改用 mock runner（固定不同 pass_rate 模擬好壞產出）＋ 真 Gemini judge。
導讀 · 怎麼讀這一頁：建議依序閱讀——① 設計原則與客觀性光譜（為何盡量去 LLM）→ ② 兩層評分架構（一個 session 怎麼變成分數）→ ③ 通用效率指標（任何場景都算的效率分）→ ④ judge 家族（各場景怎麼判「達標」：general／coding／agentic）→ ⑤ 合成公式（效率＋達標怎麼併成綜合分）→ ⑥ 實算範例（coding／general／agentic 三個真實計算）→ ⑦ 容易混淆的點。前面是機制、最後用範例把機制串起來。

1 設計原則：盡量去 LLM，能程式驗證就程式驗證

同樣是「判斷任務有沒有做好」，不同方法的客觀程度差很多。本專案的核心設計，是讓每個場景 盡量往光譜左邊（越客觀）靠——任務越能程式驗證，量測出的 skill 差異就越可信、越不受 LLM 主觀波動污染。

程式硬驗證（零 LLM）
pytest ·　json_schema ·　env_state 最終狀態
零 LLM 行為訊號
規則式 completion detector
（看使用者後續回覆）
LLM judge（後備）
grounded / ppt_outline / cross_doc
／ coding 四維軟分數

→ 越左邊越客觀、越該優先採用；LLM judge 只在「沒有客觀 ground truth」時才用。 這條原則貫穿以下所有評分元件。

2 兩層評分架構總覽（決策樹）

每個 session 先算通用效率（任何場景都算），再依 resolve_task_type 與 task 指定的 judge 分流評分， 最後合成綜合分、跨 task 平均選 winner。下圖畫的是最早的 coding／general 兩分支；實際上「general」那條已擴展成 一整個可插拔的 judge 家族（見下方第 4 區），每種 judge 有自己的 check 欄位與達標方式。

3 通用效率指標（不依賴 LLM、任何場景都能算）

對應 refiner/generic_metrics.py，全部從 session 既有欄位取得。「越少越好」→ 在 cohort 內反向正規化。

指標來源方向權重
num_turns對話輪數越少越好0.35
elapsed_sec執行時間（ended−started）越少越好0.25
num_tool_calls工具呼叫總數越少越好0.15
tool_error_rate工具錯誤佔比越低越好0.15
response_chars回覆總字數（≈ token 成本）越少越好0.10
  • cohort 分組：明確按 (goal, task) 分桶，只在「同 goal 同 task 的變體群」內做 min-max 反向正規化 （不跨 task／goal 比較，避免難易度污染）。最小值→1.0、最大值→0.0；全相等或單一變體→1.0（中性）。
  • 缺值：某項在 cohort 全缺（如 mock 無真實時間）→ 不計入，權重按剩餘項重分配（分母只算有值的項）。
  • 防呆：效率「越少越好」，單獨用會獎勵擺爛 → 一定與「完成度」相乘（先確認完成，再比效率）。

評分標準（單一指標怎麼從原始值變成 0..1）

正規化（越少越好）：norm = (cohort最大值 − 本值) / (cohort最大值 − cohort最小值)
tool_error_rate（本身已 0..1）：norm = 1 − error_rate
efficiency = Σ(norm_i × 權重_i) / Σ(有值項的權重)

正規化示意（同一 cohort 三個變體的 num_turns，機制說明）

假設某 (goal, task) 下三個變體的對話輪數分別為 3 / 6 / 9（cohort min=3, max=9）：

變體num_turns計算該項 norm
v_a3（最少）(9−3)/(9−3)1.0
v_b6(9−6)/(9−3)0.5
v_c9（最多）(9−9)/(9−3)0.0

每個指標都這樣算出 0..1，再依上表權重加權平均，得該 session 的 efficiency_score。 若 cohort 三個變體輪數都一樣（如都 5）→ max=min → 該項一律給 1.0（無鑑別度、不懲罰）。

4 評測 judge 家族（各場景怎麼判「達標」）

這一區把「達標判定」的所有分支收在一起：先看家族總表，再逐一看 general／coding／agentic 三種怎麼判達標。 達標（completion）不是只有一種算法。task.json 的 judge 欄位決定該任務用哪個 judge， 對應 refiner/e2e_general.py::_CHECK_KEYS。從「LLM 對照來源材料」到「程式硬驗證（零 LLM）」都有—— 任務越能程式驗證，達標判定就越客觀。

judge適用場景check 欄位達標方式（硬 / 軟）
grounded依來源材料綜整（新聞彙整） coverage / faithfulness / conflict_handling / formatLLM 對照來源材料評分
ppt_outline論文 → PPT 大綱 coverage / structure / granularity / faithfulnessLLM（重結構/顆粒度）
cross_doc跨多份長文獻交叉比對 coverage / cross_reference / conflict_handling / faithfulnessLLM（重跨文引用/衝突）
json_schema嚴格結構化輸出 schema_valid / required_coverage / content_faithfulness jsonschema 程式硬 gate（0.7） ＋ LLM 內容忠實度（0.3）
env_state多步驟 agentic 工具流程 state_correct / order_correct / no_illegal_writes 模擬環境最終狀態程式驗證（零 LLM）
  • coding 是特例：可視為「pytest judge」——有客觀 ground truth（測試通過率），見下方 4.2。
  • per-task 插拔：同一批 pipeline 可混用不同 judge；回測對每個 (skill×task) 跑 ROLLOUTS=3 次取 mean±std，降低單次 LLM variance。
  • 硬 gate 為王：json_schema／env_state 的達標主要由程式決定（像 coding 的 pytest），最能拉開弱 baseline；純 LLM judge 在強模型 × 偏易任務時容易全員高分（天花板）。

4.1 general 達標：規則式 detector（使用者行為訊號，零 LLM）＋ LLM 後備

對應 refiner/completion_detector.py。思路來自 IR／推薦系統的 implicit feedback——不問「滿意嗎」， 看使用者接下來的回覆。純關鍵詞／正則／difflib，不呼叫 LLM。

訊號方向權重觸發例
positive（確認滿意）達標 ↑1.0「就是這個」「thanks」「lgtm」
adopt / adopt_tool（採用產物）達標 ↑1.0 / 0.7「已套用」；成功 apply_patch/write
continue_next（接續新任務）達標 ↑（弱）0.6「接著寫英文版」「next」

negative（否定、要求重來）未達標 ↓1.0「不對」「重寫」「wrong」
coding_retry（要求繼續修）未達標 ↓0.9「還是失敗」「still failing」
reformulation（重述同一需求）未達標 ↓0.8×相似度下一輪 prompt 與前輪相似度 ≥ 0.7

評分標準（訊號 → completion / confidence）

pos = Σ正向訊號權重     neg = Σ負向訊號權重
raw = (pos − neg) / (pos + neg)        # ∈ [−1, 1]
completion = (raw + 1) / 2             # ∈ [0, 1]，≥0.5 判定「達標」
confidence = tanh(pos + neg)           # 訊號越多越有信心；門檻 0.5

訊號 → 分數 對照（機制說明，非最終綜合分）

「讚，就是這個，謝謝」positive(1.0)1.0 / 01.0tanh(1.0)=0.76 ≥0.5 → 用規則達標
「不對，這不是我要的，重寫」+「還是不行」negative×2(2.0)0 / 2.00.0tanh(2.0)=0.96 → 用規則未達標

限制：行為訊號在多輪真實對話最有效（Phase 2）。Phase 1 headless 單輪、無後續回覆 → confidence=0 → 自動退回 LLM judge（末列）。general 任務的評分會標記 completion_source（rule／llm）以示來源。

4.2 coding judge：pytest 硬指標 + 四維 LLM judge 軟指標

judge 家族中「有客觀 ground truth」的一員——測試通過率是硬證據。

硬指標（客觀 ground truth）— run_pytest

在該 (變體×task) 的獨立 workspace 跑 pytest -q，用 regex 抓 N passed / N failed / N error：

情境passed/totalpass_rateall_pass（決定成功）
全部通過5 / 51.0✓
部分通過3 / 50.6✗
多數失敗2 / 50.4✗
找不到測試 / timeout / 例外0 / 00.0✗

total = passed + failed + errors；all_pass = (total>0 且 passed==total)， 是 coding 任務 _success 的判定依據。

軟指標（LLM judge）— JUDGE_SYSTEM，四維加權

維度評什麼權重1.0 / 0.5 / 0.0 例
task_completion是否達成 coding 目標（測試通過是強證據）0.55全過 / 部分過 / 全錯
response_quality修正的正確性、完整性、清晰度0.30乾淨最小修 / 可用但雜 / 誤導
tool_usage工具使用是否適當有效0.10精準 / 尚可 / 亂用
efficiency是否避免無謂重試／繞路0.05直達 / 小繞 / 鬼打牆
judge.overall = 0.55·task_completion + 0.30·response_quality
              + 0.10·tool_usage    + 0.05·efficiency   （各維 clamp 到 [0,1]）

本次 Gemini 實跑（task_001 · v_a）：四維皆 1.0 → overall = 0.55·1.0 + 0.30·1.0 + 0.10·1.0 + 0.05·1.0 = 1.0。 Gemini 一次就把 String Calculator 全部修對（5/5 通過），故各維滿分；rationale： 「single turn、100% pass rate、correct/complete/efficient」。 公式示意：若四維為 0.8/0.8/0.85/0.8 → overall=0.803。 真實 LLM 模式下四維由模型實際評分、會分化。解析失敗或任一維非數字 → 回 None（該 session 只用硬指標）。

4.3 agentic env_state judge：工具迴圈 + 最終狀態程式驗證

最難、也最客觀的一類任務：不是單次生成，而是讓 Gemini 用真正的 function-calling （refiner/tool_agent.py::run_tool_agent）對一個 in-memory 模擬環境 （refiner/sim_env.py）一步步操作，跑完後由 env.verify() 檢查最終狀態。達標完全不經 LLM。

# env_state 達標（純程式，零 LLM）
completion = 0.7 × state_correct      # 該做的做了、金額/庫存/扣點對、不該動的沒動
           + 0.2 × order_correct      # 任何寫入前，必須已先查政策（順序依賴）
           + 0.1 × no_illegal_writes  # 沒有任何違反業務規則的寫入落地

兩種環境：有防呆 vs 無防呆

環境情境env 是否把關意義
ops-workflow退款審核 / 退貨庫存（refund/restock）有硬性防呆 違規寫入被 env 擋下、不改狀態；no_illegal_writes 幾乎恆為 1 → 幫弱 baseline 兜底

四軸難度（ops-approval）：① 多相依步驟（查政策→判資格→排序→受預算核銷→連動扣點→通知）； ② 政策衝突需推理（fraud > FINAL 不可退 > VIP 窗 > 基本窗）；③ 長 horizon（每日預算上限，須累計、超過 defer）；④ 無防呆。

此情境的實跑對照數字（通用 vs 專用 skill）見下方第 6 區「實算範例 ③」。

5 合成綜合分公式（依任務類型）

前面各元件（效率、judge/detector 達標）算完後，依任務類型合成單一「綜合分」。三種任務三條公式， 共同精神＝先確認完成度、再讓效率加成，擺爛不會因為快而勝出：

# coding：pytest+judge 為主體，效率僅 ±5% 微調（向後相容）
base  = 0.6 × pass_rate + 0.4 × judge.overall
score = base × (0.95 + 0.05 × efficiency)

# general：完成度為主體，效率在「已完成」前提下加成 ≤40%
score = completion × (0.6 + 0.4 × efficiency)

# agentic env_state：completion 本身即程式驗證分數（見 4.3），不再乘效率

_success 判定：coding 用 all_pass（測試全過）；general／env_state 用 completion ≥ 0.75。 最後同一變體跨 task 平均綜合分選出 winner，送進 execution 精煉。

7 容易混淆的點

三種 judge 來源，公式相同：① 版本 A 真實 LLM（JUDGE_SYSTEM） ② 版本 A 離線 mock（base=0.8）③ 版本 B SkillClaw 原生 session_judge——同一組四維權重。
「評分閘」≠「發布閘」：綜合分用來比較變體選 winner； verifier.py 的 0.75 門檻是另一道獨立的「精煉版能否發布」閘 （grounded / preserves value / specificity / safe 四 check）。
客觀性光譜：同為「達標判定」，客觀程度不同——env_state／json_schema 由程式硬驗證（完全不經 LLM）最客觀；general 的規則式 detector 次之（零 LLM，但靠行為訊號）； grounded／ppt_outline／cross_doc 仍需 LLM 對照。任務越能程式驗證，skill 差異的量測就越可信。
